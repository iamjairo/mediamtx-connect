# Phase 4 — Production-ready releases

Scope is "make the standalone forms releasable." Phase 3 shipped the
artifacts (dashboard container, compose file, Tauri shell); Phase 4
makes them installable, updatable, and multi-arch — sized for personal
use (no commercial code signing yet, no turnkey launcher).

## Workstreams (all four ship together)

### 1. MCP tray app — `apps/mcp-tray/`

A small Tauri 2 **menubar/tray** application — distinct from the
`apps/desktop/` dashboard wrapper:

| Aspect       | `apps/desktop/` (Phase 3)       | `apps/mcp-tray/` (Phase 4)        |
|--------------|----------------------------------|------------------------------------|
| Purpose      | Dashboard UI in a window         | MCP server lifecycle manager       |
| UI           | Full window with the dashboard   | Tray icon + small settings popup   |
| Process      | Single webview                   | Supervises `node dist/index.js`    |
| Persists     | MediaMTX connection settings     | MCP env vars + auto-start flag     |

Features:
- Tray icon (Apple menubar, Windows tray, Linux systray) with a state
  dot (running / stopped / error).
- Tray menu: Start, Stop, Restart, Show logs, Settings, Quit.
- Small settings window: `MEDIAMTX_URL`, basic-auth creds,
  `MEDIAMTX_MCP_ALLOW_KICK` toggle, auto-start on login.
- Log viewer window that tails the child process's stderr/stdout.
- The bundled `node dist/index.js` is the MCP server from `mcp-server/`
  packaged inside the Tauri resources dir.

Why: makes the MCP server installable by a non-developer. Right now
you have to `npx @iamjairo/mediamtx-mcp` from a terminal or hand-edit
`claude_desktop_config.json`. The tray app lets you install a `.dmg` /
`.msi` / `.AppImage`, configure once, and the MCP server is just there.

### 2. MCP streamable-HTTP transport

`mcp-server/src/index.ts` currently always uses stdio. Add a transport
switch driven by env:

```
MEDIAMTX_MCP_TRANSPORT=stdio       # default (Claude Desktop, Claude Code)
MEDIAMTX_MCP_TRANSPORT=http        # always-on container, remote clients
MEDIAMTX_MCP_HTTP_PORT=8181        # only used when transport=http
```

The 2026-07-28 MCP spec is stateless at the protocol layer, so HTTP mode
is a plain Node HTTP server using the `StreamableHTTPServerTransport`
from `@modelcontextprotocol/sdk`. Sticky sessions and shared session
stores are not required.

This unlocks the `deploy/docker-compose.yml` `mcp-server` service moving
out of the `[mcp]` profile and becoming always-on, with its port
exposed.

### 3. Release CI matrix — `.github/workflows/release.yml`

Triggers on `v*` tags. Builds and publishes:

| Artifact            | Platforms                                 | Target                       |
|---------------------|-------------------------------------------|------------------------------|
| dashboard image     | linux/amd64, linux/arm64                  | ghcr.io/iamjairo/mediamtx-dashboard |
| mcp-server image    | linux/amd64, linux/arm64                  | ghcr.io/iamjairo/mediamtx-mcp |
| dashboard desktop   | linux x64+arm64, macOS x64+arm64, win x64+arm64 | GitHub Release assets  |
| mcp-tray desktop    | linux x64+arm64, macOS x64+arm64, win x64+arm64 | GitHub Release assets  |

Build matrix:
- Docker images via `docker/buildx-action`, multi-arch via QEMU on
  ubuntu-latest.
- Tauri bundles via the standard matrix-per-OS approach:
  `runs-on: ubuntu-22.04 / macos-14 / windows-2022`, with the macos run
  doubling up x64 + arm64 via `--target universal-apple-darwin`.

No code signing in this phase — for personal use, unsigned bundles are
acceptable. Code signing arrives later if/when we publish broadly.

### 4. Auto-update — `tauri-plugin-updater`

Both desktop apps get the updater plugin wired to a manifest hosted on
GitHub Releases:

```
https://github.com/iamjairo/mediamtx-connect/releases/latest/download/latest.json
```

`latest.json` is generated by the release workflow per app. Signature
verification uses a Tauri-generated key pair; the private key lives in
`TAURI_SIGNING_PRIVATE_KEY` repo secret, the public key in
`tauri.conf.json`.

User experience: app checks at launch, prompts on update available,
downloads and restarts when accepted.

## Sensible defaults applied

1. **Code signing:** skipped. Personal use; unsigned bundles work via
   right-click → Open on macOS, "Run anyway" on Windows SmartScreen,
   `chmod +x` on Linux AppImage.
2. **Telemetry:** none. No analytics, no opt-in flag, no SDK.
3. **Auto-update channel:** stable only. No beta / nightly channels.
4. **MCP server packaging in the tray app:** ship `dist/` (compiled
   ES modules) + a vendored copy of `node_modules` for a single-bundle
   approach. Avoids a runtime npm install on first launch. Cost is
   ~30 MB of `node_modules` per tray-app installer; acceptable.
5. **Tray app bundles Node?** No — relies on the user having Node 20+
   installed. (Bundling Node bloats the installer by ~80 MB; we'll
   revisit if a non-developer user reports installing Node is too much
   friction.)
6. **Update signing keys:** generated by `tauri signer generate` and
   committed (public key only) on first release. Private key lives as
   a repo secret.

## Open questions

1. **macOS notarization** — skipped for personal use. Worth revisiting
   only if the install warnings annoy you enough to set up an Apple
   Developer ID ($99/year + a notarization keychain).
2. **Tray app's "show logs" UX** — current proposal is a separate
   webview window tailing `child.stderr`. Alternative: pipe to a file
   in the platform's log dir and open with the OS default viewer.
3. **MCP HTTP auth** — the transport itself has no auth in the spec.
   In personal-use mode bound to localhost, that's fine. If you'd ever
   expose it remotely, we need a bearer-token layer.
4. **Bundling Node** — see "sensible defaults" #5. Re-decidable.
